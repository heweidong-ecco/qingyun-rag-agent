### 2.2 🔴 **顺序陷阱：中间件的【执行顺序】与【源码顺序】相反**

**这是本仓最容易写错的一条。**

Starlette 的 `add_middleware` 是 `user_middleware.insert(0, ...)`，而洋葱用 `reversed()` 包
⇒ **最后 add 的在最外层、最先执行**。

**实测真实顺序**（`import main` 后打印 `app.user_middleware`）：

```
① TextNormalizationMiddleware   ← 最先执行
② QuotaMiddleware
③ RateLimitMiddleware
④ 日志/指标（log_and_track_request）
⑤ 路由
```

> ⇒ **与 `main.py` 的源码顺序（日志→限流→配额→规范化）逐层相反。**
>
> ### ⚠️ 由此产生两个**可观察的后果**
>
> 1. **被限流/配额拒绝的请求（429）【不会经过】日志中间件**
>    ⇒ **不进 Prometheus 指标** · **没有 `X-Request-ID` 响应头**（那头在 `:96` 才加）。
>    📌 **查"为什么某次 429 在指标里看不到"时，先看这条。**
> 2. **`main.py:336` 的注释写「放在限流中间件之后」** ——
>    按**执行**语义它其实**先于**限流跑 ⇒ **配额先于限流被消耗**。
> 3. ⚠️ **配额那一层现在【要查 PG】**（2026-10-03）—— 它排在最外层的第 2 位，
>    **每个请求**（含最终被限流拒掉的）都要先付一次 `SELECT SUM(...)` 的代价。**原先没有这笔开销**
>    （旧实现是 Redis `INCR`）。

### 2.3 startup 做了什么（`:577` 起，**严格按此顺序**）

```
1. validate_config()        ← 缺 4 个必填键 ⇒ 抛 EnvironmentError，拒绝启动（fail-fast）
2. init_pool()              ← 必须早于 3（建表要连接）
3. create_table()
4. ensure_admin_exists()
5. warmup_cache()           ← ⚠️ 同步阻塞，逐个调 embedding（10 个热点查询）
6. await run_health_check() ← ⚠️ 同步等待，每个工具起一个 MCP stdio 子进程
7. create_task(scheduled_health_check())  ← 之后每 120 秒一次
```

> ⚠️ **5 与 6 都是阻塞的** ⇒ **启动会慢**。
> 📌 `APP_START_TIME` 在**模块导入期**赋值（`:447`），而 `/ready` 要求**满 10 秒**（`:456`）——
> **那是与 startup 事件无关的另一道门**。

## 三 · 两条主链（**⚠️ 它们不一样，这是关键**）

### 3.1 `POST /rag/search` —— **"管线化"的那条**

```
中间件 ①②③④ → get_current_user_hybrid → PIPELINE_FACTORIES[mode]()
  → rag_pipeline.search_async():
      清洗 → [改写] → [扩展] → 每个子查询 embedding
      → db.search_similar_async（pgvector <=>）
      → db.bm25_search_async（jieba + rank_bm25）
      → **_rrf_fusion**（k=60）
      → [reranker.rerank_async]  ← 需要 torch
      → 过滤 rerank_score < 0
      → [generate_answer → answer_with_citations]
```

**每一环都可开关**，由 `mode` 决定（4 种：`fast` / `accurate` / `accurate_norerank` / `full`）。

### 3.2 `POST /rag/stream_search` —— **"自成一体"的那条**

```
中间件 ①②③④ → get_current_user_hybrid
  → cache.get_chat_history
  → embedding_client.get_embedding
  → 🔴 【裸 SQL 直查 pgvector】  api_v1_rag.py:581-590
       不走 rag_pipeline · 不走 hybrid_search · 不走 BM25 · 不走 reranker
  → 组 prompt（citations 决定用哪套）
  → 内层 async generator：get_llm_stream().stream() 逐 chunk yield
  → append_chat_history（写回 Redis）
```

> ### 🔴 **两条链的关键差异（本仓最该知道的一件事）**
>
> | | `/rag/search` | `/rag/stream_search` |
> |---|---|---|
> | 召回来源 | **改写 + 向量 + BM25 + RRF + 重排** | **仅向量（裸 SQL）** |
> | 受 `mode` 影响 | ✅ | ⛔ **它没有 mode 参数** |
> | 用 `hybrid_search` / `bm25_index` | ✅ | ⛔ |
>
> ⇒ **同样一个 `top_k`，两条链召回的文档集不同源。**
> ⇒ **"检索结果和流式结果对不上"不是 bug，是设计如此** —— 但它**没被任何文档写下来过**，
> 直到这份。
> ⬜ **未裁**：这是有意（流式要快）还是欠账？
> （🔴 **唯一清单在它那儿**， 只剩指针）。

### 3.3 Agent 链（`/agent/mcp_chat` —— 最复杂的一条）

```
check_budget（依赖，用户级日预算）
  → mcp_agent.ainvoke()
      ├─ "agent" 节点：注入 Mem0 记忆 → check_token_budget → get_mcp_tools()
      │     （⚠️ 每次调用【新起一个 MCP 子进程】）→ llm.bind_tools → invoke
      ├─ should_continue：有 tool_calls → "tools"，否则 → "chat"
      ├─ "tools" 节点：check_multilevel_budget（单次/单线程成本，元）
```

> ⚠️ **三道独立的预算闸**（用户级日 token / 单次成本 / 单线程成本），**各查各的**。
> ⚠️ **80% 预警只在【这一个接口】的响应体里出现** —— 不推送、不落表，其他端点拿不到。

> ### 🔴 **图里【没有】接 RAG —— 这是【设计】，⛔ 不是欠账**（2026-10-12 作者口述补记）
>
> **作者原话（两段）**：
> 「当时做设计的时候，就是遇到的问题是，**没有输出能不依赖 rag 直接调用 llm 做输出** ——
> 因为**有的场景就是不在自己库里查东西，需要查外部资料**，这时候**内部的 rag 输出的内容就是噪音**。
> 所以 `/agent` 都没有 +rag；**需要内部资料兜底的，都是走 `/rag` 这里**。」
>
> 「**`api_v1_agent.py` 里面都是外部知识查询；`api_v1_rag.py` 都属于内部资料查询，有不带 llm 的、
> 也有带 llm 的 api**。……**如果给 `/agent` 接上 rag，意图识别的控制是非常难的，没办法 100% 保证不出错**
> —— 给了 `tools-rag` 这个工具，**就会有错的风险**：query 本来是查外部，**结果查了内部资料污染了**。
> 所以做了两个单独模块。……**`api_v1_rag.py` 就不同了，这个注定要查内部资料**，

> #### 两条线（**模块级就是分开的**）

> | | **`/rag/*` = 内部资料线** | **`/agent/*` = 外部知识线** |

> ⇒ 与其赌意图分类，**不如把它做成两个模块**：**各自注定只查一种**，没有判断，就没有判错。
