## 一 · 代码规范

### 1.1 这些是**已存在的事实**（从代码里抽出来的，不是我希望的）

| 项 | 现状 |
|---|---|
| 缩进 | **4 空格** |

### 1.2 注释：**本仓最有特色的规矩**

这不是"风格偏好"，是**本仓用血换来的**：

#### ⭐ 规矩 A · 注释写「**为什么**」，不写「**是什么**」

```python
# ✅ 本仓的写法（app/core/db.py:53-54）
# 注意：仅保留上方基于连接池的 get_db()（自动提交/回滚/归还连接）。
# 历史版本曾在下方重复定义 get_db() 覆盖连接池版本，导致写入不提交、连接池失效，已删除。

# ❌ 不会出现在本仓
# 定义 get_db 函数
```

**判据**：**删掉这行注释，后来的人会不会重犯同一个错？** 会 ⇒ 写。

#### ⭐ 规矩 B · 更正类注释要带**日期 + 出处**

```python
# ⚠️ 2026-09-20 删（§三·B7）：此处原有 `DB_CONFIG = {...}` —— **全仓零引用**
```

**格式**：`⚠️ YYYY-MM-DD <动作>（<出处>）：<原因>`
**出处**指： / `§三·B7`（待办登记的节号）/ `复盘 <文件名>`

**为什么**：**注释也会过期**。带日期的注释**能判断它是不是还有效**；
不带日期的注释，后人只能猜。

#### ⭐ 规矩 C · 删除代码时，**留一行说明"删了什么、为什么"**

```python
# 50:# ⚠️ 2026-09-20 删（§三·B7）：此处原有 `DB_CONFIG = {...}`
```
而不是**静默删掉** —— 否则 `git blame` 到这一行时，看到的是一个凭空多出来的空行。

#### 🔴 两个"看代码会误判"的坑（**都真栽过**）

**坑 A · 「有中间件 ⇒ 受保护」**
`RateLimitMiddleware` / `QuotaMiddleware` **只管频率与配额**，⛔ **都不校验身份**。
⇒ **鉴权完全靠路由自己的 `Depends(...)`。**
📌 实测（2026-09-30）：`api_v1.py` 的 **11 条路由里只有 1 条**带鉴权依赖,
其中 **`/rag/benchmark-embedding` 匿名可打、且【真烧钱】**（实测 HTTP 200 · 385ms 真调 DashScope）。

**坑 B · `len(app.routes)` 不等于路由总数**（**这条踩了两次**）
`FastAPI 0.141` 起，`include_router` 的结果被包成 **`_IncludedRouter`**
**直接遍历 `app.routes` 会漏掉所有子路由**（本仓实测：58 条里只能看到 **5 条**）。

```python
# ✅ 正确：递归进去，且属性名是 `original_router`（实测出来的，不是 .routes）
def collect(routes, out):
    for r in routes:
        if type(r).__name__ == "_IncludedRouter":
            collect(r.original_router.routes, out)
        elif type(r).__name__ == "APIRoute":
            out.append(r)
```

#### 🔴 **WebSocket 路由也要鉴权** —— 但 ⛔ **不能照抄 HTTP 那套**（2026-10-05）

## 二 · 提交规范

> 📌 **这一节的详细版在 `CLAUDE.md` 的「推送节奏」与「判据纪律」两节** —— 此处只列要点，不复制。

### 2.1 提交信息

**格式**：`<类型>(<范围>): <一句话>`

| 类型 | 用在哪 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `chore` | 杂项（依赖、配置、gitignore） |
| `refactor` | 重构（不改行为） |

**本仓的实际写法**（从 `git log` 看）：中文描述 + 必要时多行展开"为什么"。

### 2.2 **两个门的两问**（⛔ 每次 commit 都要答）

1. **「这次改动里，有没有在多个方案之间做过选择？」**
   有 ⇒ **建一份 `DEC-nnn`**（含备选方案 / 评估标准 / 反悔成本）
   无 ⇒ **在 commit message 里写明「本次无决策事项」**
   📄 **空壳模板** ⇒ **`docs/DEC-选型模板.md`**（🔴 **2026-10-05 批 4 才补上** ——
   在此之前，用户级钩子那句提示在**本仓**指的是**一条空的路径**：见  §五·2 第 3 条）
2. **「CHANGELOG 写了吗？」** 没写 ⇒ **先补，再 commit**

### 2.3 推送节奏（**2026-09-30 改版**）

* 🔴 **推送：小批多次** —— **按段推，别攒成一大批**。
  **为什么**：**GitHub 自动风控对「批处理」形态敏感**（2026-09-24 账号被封 5 天）。
  📄 本仓的决策记录（⛔ 不随产品仓提供）
* ✅ **提交：仍然【攒着】—— ⚠️ 推送分次 ≠ 提交分次**

  > **一个 PR 的活儿，提交可以攒着一次建；⛔ 不必"一个文档一个 commit"。**
  >
  > ⚠️ **这条是 2026-09-30 补的** —— 当天 **AI 把 （推送给分成多次）错误地延伸成了
  > "每个文档一个 commit"**，被需求方当场指出「**一个文档没必要一个 commit**」。
  > **改版只动【推送】，没打算动【提交】。**

* 🔴 **❌ 一件事没处理完，不 commit。**（2026-09-30 加 · **同一天栽了两次后才写死**）

  > **判据（一条，可当场问自己）**：
  > ### 「我这条 commit 发出去，**接手人会不会以为这件事结束了**？」
  > **会 ⇒ 还不到 commit 的时候。**
  >
  > 📌 **本仓 2026-09-30【同一天栽了两次】**：
  > | 第几次 | 怎么栽的 |
  > |---|---|
  > | **第一次** | 改完一份文档就 commit 一次 ⇒ 需求方：「**一个文档没必要一个 commit**」 |
  > | **第二次** | **刚记下上面这条**，转头又**在 B1–B14 还没裁完时就 commit** ⇒ 需求方：「**不是还没有处理完吗，等下一起 commit**」 |
  >
  > ⇒ ⚠️ **第一次的措辞（"可以攒着"）不够狠** —— 它读起来像"**也可以不攒**"。
  > **现在改成禁止式**：**没处理完 = 不许 commit**，不是"建议攒着"。
  > ⚠️ **反过来说**：**"处理完"由【需求方要的那件事】界定，不是由"我手上告一段落"界定。**

* ✅ **「一个可验证单元」这条没变** —— 但**它管的是「做完没做完」，不是「多久推一次」**。
* ⛔ **`git` 挂了先分清「抖动」还是「拦截」** —— 处置相反（重试 vs 换通道）
* ⚠️ **本地 = 不 durable** ⇒ **当天结束前至少推一次**

> 📌 全文见 `CLAUDE.md`。

### 2.6 ⭐ **删已合并分支 —— 三条判据**（2026-10-02 立 · **当天绕了几个来回**）

> **背景**：本仓一律 **squash-merge**（一个任务一个 PR ⇒ 主干上一个 commit）。
> 那之后想删掉那条来源分支，**`git` 自带的两个提示全都是错的。**

### 🔴 两条【看起来行、其实不行】的

| ⛔ 看起来能判 | 它实际在说什么 |
|---|---|
| **`git branch -d <分支>` 报「not fully merged」** | **squash 造的是一个【新提交】** —— 主干上**根本没有那个 commit id** ⇒ `git` 判它"未合并"。<br>⚠️ **这不是"真没合"，是这条命令量不到 squash。** 它会**劝你用 `-D` 强删** —— 而 `-D` 是**真盲删** |
| **`git diff <主干>..<分支>` 非空** | **两种形式都答非所问**：<br>· **两点 `main..feat`** 比的是**两个末态的差异** —— 主干在合并后往前走一步，它就非空，**与分支合没合无关**<br>· **三点 `main...feat`** 自 `merge-base` 比 —— **任何做过事的分支都非空**，**连"已合并"的也非空** ⇒ **永远分不出来**<br>📌 同理 `git log main..feat` 也非空（它比的是 commit id，不是内容） |

> ### ⭐ 概括：**它们回答的都是「主干和分支的【提交 id】像不像」，而我要问的是「分支上的【内容】进没进主干」。**
> **⬆️ 与 §3.0·6 同一个病**：判据的实现与意图不一致，**而它不报错，只给一个数。**

### ✅ 三条真判据（**全部要过** —— 已在 `/tmp` 探针仓里实测过）

| # | 判据 | 命令 |
|---|---|---|
| **1** | **该分支的 PR 已 `MERGED`** | `gh pr view <n> --json state,mergedAt` ⇒ `"state":"MERGED"` |
| **2** | **分支 tip 的时间【早于】合并时间** | 分支在 PR 合完**之后又提交过** ⇒ 那些提交**不在 PR 里** ⇒ **不许删** |
| **3** | ⭐ **分支 tip 的【树哈希】能在主干历史里找得到** | 见下 —— **这是最强的一条** |

```bash
# 判据 3：树哈希（squash 之后，【树】应当一致 —— 提交 id 不同，树相同）
TIP_TREE=$(git rev-parse "<分支>^{tree}")
git log --format='%T' -n 200 origin/main | grep -qF "$TIP_TREE" \
  && echo "✅ 内容在主干上" || echo "⛔ 分支上有东西没进主干 —— 别删"
```

- **为什么用【树】不用【提交】**：**squash 换掉了提交 id，但没换内容** ⇒ **树哈希相等正是"内容一样"的定义**。
- **判据 3 顺带覆盖 2**：分支若在合并后又提交过，**它的 tip 树就不会出现在主干历史里** ⇒ 直接拦下。
- ⛔ **别用 `-D` 绕过** —— 它的语义是「**我确认要盲删**」。
  **要删就说明三条判据过了**，而不是"git 不让我删所以我强删"。

> 📄 **同族**：本仓的复盘记录（⛔ 不随产品仓提供） · §3.0·6（**判据自证：如果它错了会表现成什么样？**）

### 2.6·5 ⭐ **开新分支后，先核【它从哪儿分出来的】**（2026-10-06 立 · **当天误开到 PR 页多出 4134 行**）

> **背景**：`git checkout -b <名>` 的 base 是 **`HEAD`**，⛔ **不是 `main`**。
> 上一件事的分支还停在 `HEAD` 上时开新分支 ⇒ **新分支是从上一件事分出去的**。
> ⚠️ **它本地几乎不可见**：`git status` 干净、`git log origin/main..HEAD` 只有本意中的 commit、
> **`git diff --stat origin/main HEAD` 打【空】**（squash 之后两边树一样）—— **三条全"正常"**，
> 而 GitHub 的三点 diff 会把上一整批算成你带来的。📄 全程 ⇒ 本仓的复盘记录（⛔ 不随产品仓提供）

**开完分支，跑这一行**：

```bash
test "$(git merge-base origin/main HEAD)" = "$(git rev-parse origin/main)" \
  && echo "✅ base 对" || echo "🔴 base 错了 —— ⛔ 先别开 PR"
```

**开完 PR，再核第二道** —— 拿 diff 规模跟「我这次改了几个文件」对：

```bash
gh pr view <n> --json changedFiles,additions,deletions
```

⚠️ **栈式 PR 是例外** —— 那时 base **有意**不是 `main`，别套这条（见 §2.7）。

### 2.7 ⭐ **栈式 PR 的收尾 —— 三条坑**（2026-10-03 立 · 实测于 `#71` → `#72`）

> **什么场景**：子 PR 的基分支是**父 PR 的分支**（本仓用它的理由：需求方裁「排在  之前」的**插单**，
> ⛔ 不能折进父 PR —— 那会让父 PR 的差异面变成两件事）。
> 父 PR 被 **squash** 合进 `main` 之后，子 PR 要收尾。**三条都不是想得出来的，是实测出来的。**

| # | 坑 | 症状 | ✅ 做法 |
|---|---|---|---|
| **1** | **GitHub 不会**自动把子 PR 的基分支改指 `main` | 子 PR 仍指着父分支 —— 那个分支「已并入主干、但它的 SHA 不在主干上」⇒ **合不进 `main`** | 显式 `gh pr edit <n> --base main`<br>⚠️ 它**只在基分支被【删掉】时**才自动改指 —— 「父 PR 合了」**不算** |
| **2** | ⛔ **别用 `git merge origin/main` 收尾** | 实测在 **6 个文件**上冲突（`CHANGELOG.md` · `ROADMAP.md` · 本仓的决策记录（⛔ 不随产品仓提供） · `app/agent/specs/agent_graph.md` · `docs/待办总表.md` · `docs/说明/测试.md`）<br>**根因**：merge 的 3-way 基是**旧 main** ⇒ **父 PR 的改动在两边都成了「新增」** ⇒ 全冲突 | `git rebase --onto origin/main <父分支的原 tip sha>`<br>—— 只把子 PR 那**一条** patch 重放到新 main 上。<br>**实测零冲突**；rebase **前后树哈希一致**（`1a08df4…`）⇒ **内容一条没丢**（验证方式就是比树哈希，见 §2.6 判据 3）<br>然后 `git push --force-with-lease` |
| **3** | ⛔ **`gh pr edit <n> --base main` 【不会】触发 CI** | 改基分支发的是 `pull_request` 的 **`edited`** 事件，**不在默认活动类型里**（默认只有 `opened` / `synchronize` / `reopened`）<br>⇒ `main` 有 required checks ⇒ PR 卡在 **`mergeStateStatus: BLOCKED`**，而 `gh pr checks` 报 **「no checks reported」**——⛔ **别误判成「CI 挂了」** | `gh pr close <n>` + `gh pr reopen <n>`（发 `reopened`，在默认类型里）<br>⛔ **不用**往分支塞空提交 —— **no-op push 不产生 `synchronize`** |

> ### 🔴 收尾后**必须按内容核**，⛔ 别只看 `state`
> ```bash
> gh pr view <n> --json state,mergedAt,mergeCommit   # ① 只是"它说合了"
> git fetch origin main -q
> git cat-file -t <squash sha>:app/新文件.py          # ② 内容真在主干上吗（读树，不读工作区）
> ```
> ### ⚠️ 比「领先几条」时，**比较基用 `origin/main`，⛔ 别用 `main`**
> `git fetch origin main` **只更新 `origin/main`，⛔ 不动本地的 `main` 分支**（fetch 从不写本地分支）。
> ⇒ 本地 `main` 会**长期悄悄落后**，`git log main..HEAD` 于是**虚高**。
> 📌 **2026-10-05 实测**：PR `#95`（`503fa19`）早已合进 `origin/main`，本地 `main` 还停在 `#94`（`3f37e28`）
> ⇒ `git log main..HEAD` 报 **5** 条，**实际只领先 4 条**。
> ⚠️ **别诊断成"fetch 没生效"** —— 实测：把 `origin/main` 人为退回 `3f37e28`，一条 `git fetch origin main` 就回到 `503fa19`。
> 是**问错了对象**，不是命令失效。要同步本地分支才写 `git fetch origin main:main`（ff-only），
> 再用 `git merge-base --is-ancestor` 核。
> 📌 **判据（可打印）**： ——
> 它把本地分支 / 本地视图 / **远端真值** 三方摆出来；本机 `main` 落后时会打 **`drift`**（退出码 1）。
> ⚠️ **别用 `[ "$(git rev-parse main)" = "$(git rev-parse origin/main)" ]` 当判据** ——
> 那**两个都是本地视图**，相等只说明「本地自洽」（本仓的复盘记录（⛔ 不随产品仓提供））。
> 📌 本仓有「**合并已成功却报错**」的前科（`gh pr merge` 退出码非 0 而实际已合）——
> **两个方向都要防**：既防「报成功却没合」，也防「报成功只合了一半」。
> ⚠️ 合并**必须**带显式 `--subject` / `--body`，否则 `--squash` 会把分支上**所有** commit 的正文
> 拼进主干那条 commit（实测过一次 **114 KB**，不可逆）。

> ⬆️ **接 §3.0·5** —— 那一节治的是「**没跑命令，凭记忆写数字**」。
> 这一节治的是**下一层**：**命令跑了，但那条命令量错了东西。**
>
> 📄 **全文 ⇒ 本仓的复盘记录（⛔ 不随产品仓提供）**

### 🔴 要害：**歪掉的判据不报错**

它**不抛异常、不返回空、退出码 0** —— 它**照常打印一个数**，
而**一个整数看起来永远像一个答案。**
⇒ **「我核过了」这件事本身会给虚假的安心感。**

| 我写的 | 它实际在量 | 我想让它量 |
|---|---|---|
| `grep -rn "ChatOpenAI(" app/` | **文本里有没有这个串** | **代码里有没有这个调用** |
| `grep -o '\|'` | **字符出现了几次** | **这张表有几个单元格边界** |

### 五条（**照做**）

| # | 规矩 | 为什么 / 怎么做 |
|---|---|---|
| **1** | ⭐ **数之前先分清：我数的是【字符】还是【结构】** | 两者**都不是**「这个串出现几次」 |
| **2** | ⭐ **数【代码里的调用】⇒ 先剥注释** | `grep -v '^\s*#'` **只挡整行，⛔ 挡不住行内 `# ...`** ⇒ **要挡行内就得真剥**：<br>`python -c "… print(l.split('#',1)[0].count('ChatOpenAI(')) …"`<br>📌 **本仓纪律早有同款**（`CLAUDE.md` 判据 #2「别只数'替换了几处'，注释里也有同样的串」）<br>⚠️ **但那条只管到"替换"** —— **"数"同样适用，这次就是栽在把"数"漏出去** |
| **3** | ⭐ **数【结构】⇒ 先消转义再数** | GFM 表内代码段的 `\|` 渲染回 `\|` ⇒ 它**不是**单元格边界。<br>`sed 's/\\\|//g' \| grep -o '\|'` ⇒ **真边界数**；另起一条数转义 ⇒ **转义数**。<br>**两个数分开报**，⛔ 别只报总和（差 1 就够让你判错表坏没坏） |
| **4** | ⭐ **反直觉的数 ⇒ 先怀疑判据，⛔ 别顺手写进结论** | 预期 0 得 3、预期 4 得 5 ⇒ **停下，换另一种数法重数**。<br>⚠️ **若那个假数字恰好落在合理区间 ⇒ 今天就会静默通过** ⇒ **别把防错押在"我觉得不对"上** |
| **5** | ⭐ **判【集合差异】⇒ 用集合运算，⛔ 不用 `diff`**（2026-10-05 加） | `diff` **按行序对齐**，**不是集合比较工具** —— 两边**都有的行**，只要**上下文行不同**就会被报成「新增 / 删除」。<br>✅ **去注释 / 去版本号 ⇒ `sort -u` ⇒ `comm -13`（只在 B）/ `comm -23`（只在 A）**。<br>`diff` 只用来读「**改了哪几行**」，⛔ **不用来判「多了少了什么」**。<br>📄 本仓的复盘记录（⛔ 不随产品仓提供） —— 那次**扩散到 3 处并推送出去**，还**被当成裁决依据呈给了需求方** |

### ⭐ 判据自证（**治本的那一条**）

> **每条【自造】判据，配一句：如果它错了，会表现成什么样？** —— **答不出 ⇒ 这条判据还没写好。**

- 例：**故意写一行 `# ChatOpenAI(` 的注释**，看它数不数 ⇒ **数出来 = 这条判据会误报**
- 📌 **同族三条，都是「判据的实现与意图脱节，且脱节时不报错」**：
  本节的 #2 ·  连带影响 ①（「判据不能依赖两个东西恰好不同 —— 那个不同会被一次无关修改消掉，
  **消掉后判据不报错，只会静默变成永远通过**」）· 本仓的复盘记录（⛔ 不随产品仓提供）

### 3.1 ⭐ 「**一份内容只在一处**」—— 判据是脚本，不是记忆

> **2026-09-29 立。** 立它的直接原因是 **同一天实撞了三次**：
> `CLAUDE.md` 的架构节 vs `docs/原理/架构.md` · `ROADMAP` 的「生产级」vs `README` 已删该词
> `ROADMAP` 里「阶段②」**两份完全相同的拷贝**。

**判据一句话**：
> **「删掉这句，另一处还能不能查到？」**
> * **能** ⇒ 这里是**多余的** ⇒ 改成**指针**
> * **不能** ⇒ 这里就是**权威** ⇒ **别处不许再写**

```bash
# 查一句话是不是被写了两遍（把整句贴进去搜）
grep -rn "要查的那句话" --include="*.md" . | grep -v "归档\|历史/\|CHANGELOG"
```

**为什么这条要写成规矩**：**它的形态很隐蔽** —— 「两边都写了」**不会报错、不会变红**，
而且**往往是同一个人（我）在修一边的时候，另一边正在被写**。

### 3.1·5 ⭐ **写「占位符」时，别把它写成像真路径的样子**（2026-09-29 立）

**判据**：凡是要写**示意性的文档名**（**不是真路径**），**别把它写成"目录 + 后缀"的样子** ——
**链接检查器会把那个名字当成本仓的一个真文件去解析**，然后报「🔴 真断链」。

✅ **正确写法**：**用文字描述**，例如

> 「`app/<组>/specs/` 下**与模块同名的那份**」
> 「`app/` 下的某个**模块**」

⛔ **错误写法**：**把示意名写成"目录 + 后缀"**（即看起来像一个真文件路径）。

> ### 😅 **本节【故意不举例】** —— 因为**举例本身就会被自己的门拦**。
>
> 📌 **这不是偷懒，是这条规矩的最好说明**：**"看起来像路径"就是会被解析成路径。**
> ⚠️ **而 `Bash`/`Edit` 那一侧不受影响** —— 门只查**反引号里的 `.md`**。
> （所以 `app/` 下的 `.py` 示意名**不会**被拦；**只有 `.md` 会**。）

> ### 🔴 它是怎么被发现的：**同一个错，一天之内犯了【4 次】**
>
> | 次序 | 在哪 |
> |---|---|
> | 1 | `CLAUDE.md` |
> | 2 | `app/specs/README.md` |
> | 3 | 本仓的工程配置（⛔ 不随产品仓提供） |
> | 4 | 本仓的决策记录（⛔ 不随产品仓提供） |
>
> ⚠️ **每次都是被链接检查当场抓住的** —— 但**每次都只改了眼前那一处**。
> 📌 **这恰好违反本规范 §3.2 的规则 3**：「**改一处口径 ⇒ 立刻全仓搜那个词**」。
> ⇒ **所以这条规矩不只是"怎么写占位符"，还是一条"发现了一个模式 ⇒ 立刻全仓 grep 它"的提醒。**

### 3.2 ⭐ **接手人视角** —— 四条（出自 本仓的复盘记录（⛔ 不随产品仓提供））

| # | 规则 | 判据（**照做**） |
|---|---|---|

> ⭐ **⇒ 结论是：这类规矩要【做成命令】，不能只写在文档里。**

> 📌 **上面 3.1 与 3.2 的规则 2，其实是同一个病的两种形态**：
> **「我做完了一个应该被指向 / 被引用 / 被同步的东西，但没人指它。」**

> ⬜ **待办**：把它做成**一条可跑的命令**（本仓已有先例：`check_doc_links.sh`
