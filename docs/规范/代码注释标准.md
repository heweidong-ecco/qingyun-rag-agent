# 代码注释标准 —— **一手来源 + 本仓口径**

> 📇 **这份文档管什么**：**代码里的注释与 docstring 该写什么、不该写什么**。
> ⚠️ 它**先给一手标准（PEP 8 / Google 官方指南的原文），再给本仓落到执行的那一层**。
> ⛔ **不许跳过 §二 直接看 §三** —— 本仓口径的每一条都要能追到 §二 的那一句。

## 二 · 一手标准（⚠️ 全部是**官方文本**，给原文与出处）

### 2.1 PEP 8 · Comments（Python 官方风格指南）

出处 —— <https://peps.python.org/pep-0008/#comments>

| 类别 | 原文（逐字） | 读成一句话 |
|---|---|---|
| 总则 | 「**Comments that contradict the code are worse than no comments.**」 | **过期的注释比没有更坏** —— 它会误导，还会让人不再信任其余的注释 |
| 总则 | 「Always make a priority of keeping the comments up-to-date when the code changes!」 | 注释**必须跟着代码改** |
| 该写什么 | 「Comment only what the code cannot say — the *why*, maybe the *what*, but never the *how*.」 | 只写**代码说不出来的**：**为什么**；⛔ 不写"怎么做的" |
| 块注释 | 每条「starts with a `#` and a single space」，且「indented to the same level as that code」 | 块注释**跟在它管的那段代码前面**、同缩进 |
| 行内注释 | 「**Use inline comments sparingly.**」 | **少用**行内注释 |
| 行内注释 | 「Inline comments are **unnecessary and in fact distracting if they state the obvious**.」（书里的例子：`x = x + 1  # Increment x`） | 复述代码的行内注释**要删** |
| docstring | 「Write docstrings for all public modules, functions, classes, and methods.」 | 公开的都写；格式见 PEP 257 |

### 2.2 Google Python Style Guide §3.8（Comments and Docstrings）

出处 —— <https://google.github.io/styleguide/pyguide.html>

| 小节 | 原文（逐字/近逐字） | 读成一句话 |
|---|---|---|
| **3.8.2 模块** | 模块 docstring 以「**A one-line summary of the module**, terminated by a period」开头，然后一段说「the contents and usage of the module」 | 模块开头 = **一句话摘要 + 怎么用** |
| **3.8.2.1 测试模块** | 测试模块**不需要**模块 docstring；「A docstring that merely restates the class or method name should be omitted.」 只有"怎么跑 / 有什么特殊依赖"这种**真信息**才值得写 | 测试里的注释**只写"为什么要这条用例"** |
| **3.8.3 函数** | docstring 应「describe the function's **calling syntax and its semantics**, but **generally not its implementation details**」 | 文档写**接口**，⛔ 不写实现细节 |
| **3.8.3 函数** | 「A docstring is mandatory for every function that has one or more of: being part of the public API, being nontrivial in size, having non-obvious logic.」 | 不是每个函数都要 —— **公开的 / 不平凡的 / 逻辑不显然的**才要 |
| **3.8.5 块与行内** | 「If you're going to have to explain it at the next code review, you should comment it now.」 | **该解释的地方才解释** |
| **3.8.5 块与行内** | 「**never describe the code**」 —— 假定读的人比你更懂这门语言 | ⛔ **不要描述代码在干什么** |

### 2.3 两条合起来，就是一句话

> **注释回答「为什么这么写」；文档回答「怎么用」。**
> ⛔ **两者都不是备忘录** —— 不写"谁在哪天改的"、不写"以前是什么样"、不写"当时踩了什么坑"。

## 三 · 本仓口径：**开发仓与产品仓是两套**（⚠️ 别拿一套套另一套）

| | **开发仓**（`qingyun-rag-agent` · private） | **产品仓**（`qingyun-rag-agent` · public） |
|---|---|---|
| 读者 | **我自己 + 下一个 Agent** | **招聘 / 作品** |
| 允许写 | 过程（日期 · 批次号 · `DEC-` · 台账指针）—— **那是这个仓的资产** | ⛔ **一律不写** |
| 注释密度 | 不设上限 | **见 §四** |
| 判据 | `CLAUDE.md` 那套 | **§五 那三条可打印的** |

🔴 **产品仓是一条独立的产线**，不是开发仓的镜像 —— 它是**导出**出来的，
本标准的 §四/§五 **全部落在导出脚本的规则上**，⛔ **不是逐份改产品仓的文件**
（逐份改 ⇒ 下次重跑导出又回来了）。

## 四 · 产品仓的执行口径（三层）

| 层 | 做什么 | 怎么落 | 判据 |
|---|---|---|---|
| **A** | **清过程标记** —— 日期 · 批次号（`批 7` / `①a`）· 内部编号· 台账指针（`复盘`）· 「当时 vs 现状」 | ✅ **纯机械** | §五·1 |
| **B** | **文档瘦身** —— 模块/函数 docstring 只留**摘要 + 怎么用**；**被砍掉的设计论证挪进该模块的 spec**（⛔ 不是丢掉） | ⚠️ **半机械**（按 `##` 小标题与空行切段） | §五·2 |
| **C** | **行内注释** —— 删掉**复述代码**的那种（PEP 8：`x = x + 1  # Increment x`） | ⚠️ 需逐处判 | §五·3 |

**⚠️ B 的"挪"是刻意的**（实测）：那些长 docstring 里写着 `## 为什么要有这个模块`
—— **它们是设计文档写错了地方**。而本仓**本来就有放它的地方**：`app/<组>/specs/<模块>.md`。
🔴 **但实测：spec 里并没有那些内容**（`safe_math` / `llm_factory` / `config` / `token_config` 四个都查了，**0 命中**）
⇒ **直接删会丢信息** ⇒ 所以是**挪**，不是删。

## 五 · 判据（可打印 · 跑在**产品仓快照**上）

```bash
# 1) A 层：代码注释里不该再出现过程标记 —— 期望 0
grep -rnE '20[0-9]{2}-[0-9]{2}-[0-9]{2}|批\s*[0-9①-⑨]|[①②③④⑤⑥⑦⑧⑨][a-z]?(?![\w])' \
     --include='*.py' app/ | grep -E ':#|# ' | wc -l

# 2) B 层：模块 docstring 的长度 —— 期望【中位 ≤ 6 行】且【最长 ≤ 15 行】
#    （跑法见  里那条自检）

# 3) 注释占比 —— 期望【没有任何单文件 > 25%】
```

⚠️ **三条都要在【产品仓】上跑**，⛔ 不是在开发仓（开发仓本来就该有那些东西）。
