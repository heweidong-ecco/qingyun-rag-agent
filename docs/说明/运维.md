## 一 · 服务拓扑（**5 个容器**）

| 服务 | 容器名 | 镜像 | 端口（**实测活容器**） | 对外暴露 |
|---|---|---|---|:--:|
| `api` | **`rag-api`** | `fastapi-rag-agent:latest`（本仓 build） | `8000` | 🔴 **`0.0.0.0`** |
| `postgres` | `postgres-rag` | `pgvector/pgvector:pg17` | `5432` | ✅ `127.0.0.1` |
| `redis` | `redis-rag` | `redis:7-alpine` | `6379` | ✅ `127.0.0.1` |
| `prometheus` | `prometheus` | `prom/prometheus:latest` | `9090` | 🔴 **`0.0.0.0`** |
| `grafana` | `grafana` | `grafana/grafana:latest` | `3000` | 🔴 **`0.0.0.0`** |

**数据卷**（⚠️ 名字带历史包袱）：`my-fixed-name_postgres_data` · `my-fixed-name_redis_data`
`my-fixed-name_prometheus_data` · `my-fixed-name_grafana_data`

> 🔴 **卷名为什么是 `my-fixed-name_*`**：compose 的 `name:` 是**全局的**。
> 本仓早年的项目名就叫这个，后来改成 `fastapi-rag-agent`，**但卷名写死了旧值**。
> ⇒ **这也是 2026-09-29 那次「容器名冲突」的根源**（见  决策三）。
> ⚠️ **别随手改它** —— 改了 = **挂到一个全新的空卷 = 数据全没了**。

> ⛔ **有评测在跑时不许 `docker compose up`** —— `rag-api-eval` 曾被 `agent-eval-gate` 使用。
> **每次 up 前的判据**：`docker ps --format '{{.Names}}' | grep eval` → **空即安全**（🅰️）。

## 🔴 二 · 端口暴露面（**2026-09-29 实测，两个状态不一致**）

| 服务 | compose 里写的 | **实测活容器** | 一致？ |
|---|---|---|:--:|
| postgres | `127.0.0.1:5432` | `127.0.0.1:5432` | ✅ |
| redis | `127.0.0.1:6379` | `127.0.0.1:6379` | ✅ |
| **api** | `8000:8000` | **`0.0.0.0:8000`** | 🔴 **对局域网开放** |
| **prometheus** | `9090:9090` | **`0.0.0.0:9090`** | 🔴 **无鉴权** |
| **grafana** | `3000:3000` | **`0.0.0.0:3000`** | 🔴 **默认口令** |

> ### ⚠️ 为什么这要紧
>
> 本机是一台**笔记本**，会接入不同网络（咖啡店 / 公司 / 公共 Wi-Fi）。
> **在这三个端口开着的情况下**：
> * `8000` —— **同网段任何机器都能调这个 API**。而本仓**匿名请求绕过配额**、**限流全员共用一个桶**
>   （见 `docs/契约/接口契约.md` §七）⇒ **等于一台开放式 LLM 网关**。
> * `9090` —— Prometheus **默认无鉴权**，指标全公开。
> * `3000` —— Grafana **未设 `GF_SECURITY_ADMIN_PASSWORD`**（compose 里没有这一项）
>   ⇒ 走默认 `admin/admin`。
>
> ### ✅ 处置：**已做** —— 走的是「把三个也改成回环」
>
> **五个服务全绑 `127.0.0.1`**（`api` 8000 · `postgres` 5432 · `redis` 6379 · `prometheus` 9090 · `grafana` 3000），
> 2026-10-09「安全收口」批做的（`SECURITY.md` §3.2）。
> 📌 判据：`grep -c '^      - "127.0.0.1:' docker-compose.yml` ⇒ **5**
> （⛔ 出现裸露的 `- "8000:8000"` 就是**退回去了**）。
> ⚠️ **两条仍然成立**：① 改了 `ports:` ⇒ **要重建容器才生效**（端口绑定是容器属性）；
> ② **上公网前 Grafana 仍必须显式设管理员口令** —— 绑回环只挡住了局域网。

## 三 · 常用命令

```bash
# ── 状态 ─────────────────────────────────────
docker compose ps                                    # 5 个容器状态
docker compose ps --format 'table {{.Name}}\t{{.Status}}'
docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}\t{{.CPUPerc}}'

# ── 起停 ─────────────────────────────────────
docker compose up -d                                 # ⚠️ 先跑上面那条判据
docker compose down                                  # ⛔ 不带 -v！（-v 会删卷 = 数据没了）
docker compose restart api                           # 只重启 API

# ── 重建 API（改了 Dockerfile 或 requirements 才需要）──
docker compose build api && docker compose up -d api

# ── 日志 ─────────────────────────────────────
docker compose logs -f api                           # 跟 API 日志
docker compose logs --tail=100 api
tail -f logs/app_$(date +%Y-%m-%d).log                # 宿主机上的文件日志

# ── 进容器 ───────────────────────────────────
docker compose exec api bash
docker compose exec postgres psql -U postgres -d rag_db
docker compose exec redis redis-cli

# ── 本地开发（不用容器跑 API）───────────────
bash dev.sh                                          # 起 PG+Redis 容器 + 本地热重载
```

> ⚠️ **`dev.sh` 有个已知瑕疵**：等 PG 的循环写死 `-d rag_db`（`dev.sh:12`），
> 若 `POSTGRES_DB` 改过名，**会一直等下去**。已登记在 `docs/待办总表.md` **T5**。

## 四 · 健康检查（**三个端点，用途不同**）

| 端点 | 什么时候返回 200 | 用途 |
|---|---|---|
| **`GET /health`** | **依赖全通**（DB + Redis） | **人看 / 排障**。返回 `{"status":"healthy","checks":{"database":"ok","redis":"ok",...}}` |
| **`GET /ready`** | **启动满 10 秒** 且 `/health` 通过 | **容器编排探针**。10 秒内或依赖不通 ⇒ **503** |
| **`GET /metrics`** | 总是 | Prometheus 抓取 |

```bash
curl -s http://127.0.0.1:8000/health | python3 -m json.tool
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/ready
```

> 📌 **`/ready` 返回 503 而不是 500** —— 那是**有意的契约**。
> ⛔ **别把 503 当故障**：启动后 10 秒内它本来就该是 503。
> ⚠️ **`/health` 与 `/ready` 都在限流/配额的跳过名单里**（`PUBLIC_PATHS`），否则探针会被 429 误判。

## 五 · 日志在哪

**两处，内容一样**：

| 位置 | 怎么读 |
|---|---|
| **宿主机** `./logs/`（compose 挂了 `./logs:/app/logs`） | `tail -f logs/app_YYYY-MM-DD.log` |
| 容器内 `/app/logs/` | `docker compose logs api` |

**三通道**（`app/core/logger_config.py`）：

| 通道 | 级别 | 保留 |
|---|---|---|
| 控制台（彩色） | DEBUG | — |
| 按日滚动文件 | INFO | **30 天** |
| 错误日志（单独） | ERROR | **90 天** |

每条日志带 `request_id` ⇒ **追一次请求**：`grep <request_id> logs/app_*.log`

## 六 · 备份与恢复

### ⭐ 用脚本（**推荐**）

```bash
# 备份（默认保留最近 7 份）
--keep 30       # 保留 30 份
--list          # 只列已有备份
--dir /some/dir # 换目标目录
```

**脚本做了什么**：

| 步 | 动作 |
|---|---|
| ① | 先确认 `postgres-rag` **容器在跑**（判据是 `docker ps`，不是"我以为它在跑"） |
| ② | `pg_dump`（**含 schema + 数据**） |
| ③ | ⭐ **校验**：文件 > 1KB？表定义 ≥ 6 个？—— **不能只看退出码 0**（本仓「判据」纪律第 1 条） |
| ④ | **轮转**：只删本目录里本脚本产出的文件，保留最近 N 份 |

> ### ⛔ **备份默认落在【仓外】—— 这是有意的**
>
> 目标：**`~/backups/`**
>
> **为什么不能放仓里**：备份**含全部业务数据**（知识库内容、token 用量…），
> 而本仓是 **PUBLIC 仓库** ⇒ **哪怕 gitignore 了也不该放**。
> 📌 `Product-external/` 正是本仓规矩指定的「**不能进任何 git 仓的东西**」的落点。

### ⬜ **没有自动定时** —— 要自己加

脚本**可以在 cron 里跑**，但**本仓没有配 cron**：

```bash
# 想加的话（crontab -e）—— ⚠️ 下列时间是示例，非本仓已配置
0 3 * * * cd /path/to/fastapi-rag-agent && --keep 30 >> /tmp/rag-backup.log 2>&1
```

> ⚠️ **本仓【没有】cron / launchd / 任何定时任务。** ⇒ **上云前必须补**。已登记 `ROADMAP.md`。

### 恢复（⚠️ **会覆盖当前数据，先确认**）

```bash
docker compose exec -T postgres psql -U postgres -d rag_db < <备份文件>.sql
```

> 🔴 **恢复后【必须重建向量索引】** —— `pg_dump` **不导索引**：
> ```sql
> CREATE INDEX IF NOT EXISTS documents_embedding_idx
>   ON documents USING hnsw (embedding vector_cosine_ops);
> ```
> ⚠️ **注意索引类型**：活库是 **`hnsw`**，而 `app/core/db.py:100` 写的是 **`ivfflat`**。
> 详见 `docs/契约/数据模型.md` §六。

### 卷备份（**可选，比 `pg_dump` 重**）

```bash
docker run --rm -v my-fixed-name_postgres_data:/data -v "$PWD":/backup alpine \
  tar czf /backup/pgdata-$(date +%Y%m%d).tar.gz -C /data .
```

> ⛔ **恢复卷 = 停容器 → 换卷 → 起容器**。**先备份，再动手。**
> 📌 一般**不需要**卷备份 —— `pg_dump` 够用且可读。卷备份只在"要连 PostgreSQL 内部结构一起还原"时才用。

### schema（**只有结构**）

```bash
docker compose exec -T postgres pg_dump -U postgres -d rag_db --schema-only --no-owner --no-privileges
```

> ✅ **这份已经导出并入库**：**`app/schema.sql`**（2026-09-29 建立，**从活库生成**）。
> ⛔ **别手改它** —— 重新生成即可，文件头写了命令。

## 七 · 常见故障（**先查这里，再动手**）

| 症状 | 大概率原因 | 怎么办 |
|---|---|---|
| `/health` 返回 503 且 `database: error` | PG 没起 / 密码不对 | `docker compose ps postgres` · 核 `POSTGRES_PASSWORD` |
| `/health` 返回 503 且 `redis: error` | Redis 没起 | `docker compose ps redis` |
| **`/ready` 一直 503** | ⚠️ **可能只是启动没满 10 秒** | **等 10 秒再试**。超过 1 分钟还 503 ⇒ 去看 `/health` |
| **所有匿名请求 429** | **限流对匿名是【共用一个桶】** | 等几秒；这条是**已知缺口**（`契约 §七`） |
| **LLM 调用返回 403 `Free quota exhausted`** | ⚠️ **LLM 打到了 DashScope**（而不是 DeepSeek） | 核 `.env` 的 `LLM_BASE_URL` / `LLM_MODEL_*` 四个键（见 `docs/契约/环境变量.md` §四） |
| **建镜像特别慢 / 下包超时** | 镜像源 | 已换 tsinghua。⚠️ **别改回 aliyun** |
| **`pip` 解析 20 分钟不收敛** | 宽松约束回溯 | 已裁 5 个包。**别把 `sentence-transformers` 加回来** |
| **容器起不来，报容器名冲突** | 有**别的项目**占了同名容器 | `docker ps -a \| grep -E 'rag-api\|postgres-rag'` ⇒ **删容器（⛔ 不带 `-v`）** |
| **`Connection reset by peer`（跑脚本时）** | `localhost` 解析到 **IPv6 `::1`** 被占 | **base_url 用 `127.0.0.1`，不用 `localhost`** |
| **`CERTIFICATE_VERIFY_FAILED`** | 本机有 TLS 拦截，CA 只在系统信任库 | 设 `SSL_CERT_FILE=/etc/ssl/cert.pem` |
| **改完 `.env` 不生效** | ⚠️ **`.env` 在【仓根】**，且 **Docker 是运行时注入** | 核文件位置；容器需 `restart` |

> 📌 更长的排障清单见 `docs/FAQ.md`（337 行）。

## 八 · ⬜ 运维缺口（**上云前必须补的**）

| # | 缺口 | 后果 | 登记处 |
|---|---|---|---|
| 1 | 🔴 **端口暴露面**（api / prometheus / grafana 在 `0.0.0.0`） | 同网段任何人可用 | 本文件 §二 |
| 2 | 🔴 **Grafana 无 provisioning** —— 数据源+看板是**手工配在 `grafana.db` 里**的 | **上云会"容器起来了但没看板"** |  §遗留① |
| 3 | 🟡 **备份：有脚本，但【无定时】** ——  已建（2026-09-29） | **忘了跑就是没备份** | 本文件 §六 |
| 4 | ⬜ **无告警** | 熔断/额度耗尽**不会通知你** | `ROADMAP.md` |
| 5 | ⚠️ **`pg_dump` 不导索引** | 恢复后**向量索引丢失** ⇒ 检索**退化成全表扫描** | 见下 |
| 6 | ⬜ **无资源限制**（compose 没写 `mem_limit`） | 一个容器吃满内存 ⇒ 整机卡死 | — |

> ### 📌 第 3 / 4 / 6 条：**现在做到哪一步了**
>
> | 项 | 状态 |
> |---|---|
> | **备份** | ✅ （**含校验 + 轮转 + 落在仓外**）—— ⚠️ **但没有定时**（cron / launchd）<br>🔴 **这一条的"前提"已经不在了**：定时备份是为**上云**做的，而上云已停（只走本机 docker-compose） |
> | **资源限制** | 🔴 **不作待办**（同上，前提已不在）—— ⚠️ **但 OOM 风险没消失**：创空间实测 **8 GiB / `SwapTotal=0`**<br>⇒ 改由  §二·4 的「ingest 七条上限」治（📄 待办总表 🅒） |

> ### ⚠️ 第 5 条展开（**恢复时最容易漏**）
>
> `documents_embedding_idx` 是**向量索引**。恢复数据后必须**手工重建**：
> ```sql
> CREATE INDEX IF NOT EXISTS documents_embedding_idx
>   ON documents USING hnsw (embedding vector_cosine_ops);
> ```
> 🔴 **而且这里有个坑**：`app/core/db.py:100` 里写的是 **`ivfflat`**，与**活库的 `hnsw` 不一致**。
> ⇒ **新环境首次建表会建出 ivfflat**。详见 **`docs/契约/数据模型.md` §六**。
