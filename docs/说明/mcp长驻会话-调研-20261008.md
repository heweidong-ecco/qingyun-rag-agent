## 一 · 调研什么

-B 的备选（§2.1）是「**长驻会话**：把"每次调用起一次 MCP 子进程"改成复用一个」。
要回答的是**两个经验性问题**（⛔ 不是设计问题）：

| # | 问题 | 为什么它只能实测 |
|---|---|---|
| **①** | **后台 task 持有一个长驻 `async with`，请求经队列投递** —— 这条路**走不走得通**？ | 🔴 本仓 **2026-09-20 栽过**：池化让**应用启动直接失败**（`Application startup failed. Exiting.`）。原因写在 `agent_graph_advanced.py` 的 docstring 里：`stdio_client` 基于 anyio，其 cancel scope 要求「**进入与退出在同一个 task**」 |
| **②** | 值不值：**省多少**？代价多少？ | 数字决定值不值 |

## 二 · 结论（一句话）

> ### ✅ **① 走得通，而且快约 300–500 倍；那道 anyio 坎这次【没咬人】。**
> 🔴 **但探针顺带照出一个真 bug**：服务端的 `print()` 写到了 **stdout**，而那是 MCP 的**传输通道**
> —— 现状下**每次工具调用**都产生 1 条 `ValidationError`（稳定复现）。

## 三 · 实测数据

### 3.1 现状（每次起子进程）

📌 判据：`cd app && ../venv/bin/python -c "…call_mcp_tool('calculator', {'expression':'1+1'})…"`

| 第几次 | 耗时 |
|---|---:|
| 1 | **2.42 s** |
| 2 | **2.09 s** |
| 3 | **1.93 s** |

⇒ 成本几乎全在**起子进程 + 重新 import langchain**，⛔ 不在那次工具计算上。

### 3.2 长驻会话（后台 task + 队列）

**连跑三轮**（⛔ 一次绿不算 —— 本仓：**「从不命中」与「没人违规」在机器痕迹上完全一样**）：

| | 第 1 次 | 第 2 次 | 第 3 次 | 第 4 次 | 第 5 次 | 并发 5 个 |
|---|---:|---:|---:|---:|---:|---:|
| **轮 1** | 0.0223 | 0.0046 | 0.0040 | 0.0040 | 0.0039 | 0.0214 |
| **轮 2** | 0.0253 | 0.0053 | 0.0051 | 0.0073 | 0.0063 | 0.0268 |
| **轮 3** | 0.0246 | 0.0050 | 0.0049 | 0.0048 | 0.0048 | 0.0224 |

（单位：秒。第 1 次含 `initialize()` 握手 ⇒ 稍慢；之后稳定 **4–7 ms**。）

✅ **三轮全部干净退出**，`anyio` 的 `cancel scope` 报错 **0 次**。

### 3.3 代价：内存

| 项 | 值 | 怎么量的 |
|---|---:|---|
| MCP 子进程 RSS | **84 MB** | `tail -f /dev/null \| python mcp_server.py &` 后 `ps -o rss=`（**真子进程**） |
| 对照：空解释器 | 7 MB | 同上，不带参数 |

⚠️ **一处要作废的数**：探针第一版打印过「RSS ≈ 54 MB」—— 🔵 **那是【父进程】自己的峰值**
（`resource.getrusage(RUSAGE_SELF)` 在父进程里读的），⛔ **不是子进程的**。已用 §3.3 上表取代。

## 四 · 为什么这次不咬人（与 2026-09-20 那次的区别）

**两次的区别不在"池化 vs 不池化"，在"那个 `async with` 到底横跨几个 task"。**

| | 2026-09-20（❌ 炸） | 本次（✅ 通） |
|---|---|---|
| 形状 | **会话池**：启动 task 建 · 请求 task 用 · 归还 task 关 | **actor**：一个 **holder task** 独占整个 `async with` |
| 生命周期跨几个 task | **3 个** | **1 个** |
| 调用方怎么拿到结果 | 直接从池里取 session 用 | **把请求投进队列，等一个 future**（⛔ 不碰 session） |
| 结果 | `RuntimeError: Attempted to exit cancel scope in a different task than it was entered in` ⇒ **应用起不来** | 干净退出 |

⇒ 🔴 **可复用的判据**：**只要"进入"和"退出"落在同一个 task 里，anyio 就不管你中间被谁 await 过。**
⚠️ 所以「长驻会话」的难点**不是"跨 task 共享对象"**，是**"别让别人碰那个 context manager"**。

## 五 · 🔴 顺带照出来的真 bug（**与 B 独立 · 现状就在发生**）

### 现象（稳定复现）

```
pydantic_core._pydantic_core.ValidationError: 1 validation error for
  union[JSONRPCRequest,JSONRPCNotification,JSONRPCResponse,JSONRPCError]
  Invalid JSON: expected value at line 1 column 1
  [type=json_invalid, input_value='MCP Server 启动中... 已注册 7 个工具', input_type=str]
```

📌 判据（可打印，连跑 3 次**每次都是 1 条**）：
```bash
cd app && for i in 1 2 3; do
  ../venv/bin/python -c "
import asyncio, sys; sys.path.insert(0,'.')
from agent_graph_advanced import call_mcp_tool
print(asyncio.run(call_mcp_tool('calculator', {'expression':'7*6'})), end=' ')
" 2>&1 | grep -c ValidationError
done        # ⇒ 1  1  1
```

### 根因

| 位置 | 代码 | 危险度 |
|---|---|---|
| `app/tools/mcp_server.py` 的 `run_mcp_server()` | `print(f"MCP Server 启动中... 已注册 {len(TOOLS)} 个工具")` | 🟡 启动时一次 |
| `app/tools/mcp_server.py` 的 `list_tools()` | `print(f"工具 {tool_name} 不健康，已从工具列表中移除")` | 🔴 **它跑在 `tools/list` 请求【当中】**，正是客户端等响应的时候 |

🔴 **stdout 就是 MCP 的 stdio 传输通道** —— 往它写一个字面字符串，就等于往协议里插一句话。
2.x 的客户端把它当 JSON 解析 ⇒ `ValidationError`。

⚠️ **现在不致命**（客户端记一条错就过去了，调用照常返回 `42`），
**但它是"靠运气"** —— 本仓立场：**一个每次都报的错，⛔ 不该因为它不影响结果就当没事**。
📌 **建议修法**：两处 `print` 改成 `sys.stderr`（或 logging），并**加一条守卫**钉住
「`mcp_server.py` 里除了传输以外不往 stdout 写」。

## 六 · 探针脚本（可复现）

```python
"""调研 spike ①：后台 task 持有一个长驻 stdio MCP 会话，请求经队列投递。"""
import asyncio, sys, time, resource
sys.path.insert(0, "<repo>/api")
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client
from pathlib import Path

SCRIPT = Path("<repo>/app/tools/mcp_server.py")
PARAMS = StdioServerParameters(command=sys.executable, args=[str(SCRIPT)])
LOOP = None


class _Req:
    __slots__ = ("name", "args", "fut")
    def __init__(self, name, args):
        self.name, self.args, self.fut = name, args, LOOP.create_future()


async def _holder(q, ready, done):
    """🔴 会话的 async with 生命周期【整个】落在这一个 task 里（这是那道坎的解法）。"""
    try:
        async with stdio_client(PARAMS) as (read, write):
            async with ClientSession(read, write) as session:
                await session.initialize()
                ready.set_result(True)
                while True:
                    req = await q.get()
                    if req is None:
                        break
                    try:
                        r = await session.call_tool(req.name, req.args)
                        req.fut.set_result(r.content[0].text)
                    except Exception as e:            # noqa: BLE001
                        req.fut.set_exception(e)
    finally:
        if not done.done():
            done.set_result(True)


async def main():
    global LOOP
    LOOP = asyncio.get_running_loop()
    q = asyncio.Queue()
    ready, done = LOOP.create_future(), LOOP.create_future()
    task = asyncio.create_task(_holder(q, ready, done))
    await ready

    async def call(i):
        req = _Req("calculator", {"expression": f"{i}+1"})
        await q.put(req)
        return await req.fut

    for i in range(5):
        t = time.time(); r = await call(i); print(f"  {i+1} {time.time()-t:.4f}s -> {r}")

    t = time.time()
    rs = await asyncio.gather(*[call(100 + i) for i in range(5)])
    print(f"  并发5 {time.time()-t:.4f}s -> {rs}")

    q.put_nowait(None)
    await done
    task.cancel()


asyncio.run(main())
print("  ✅ 退出干净")
```

## 七 · ⚠️ 仍未验证的（诚实边界 · ⛔ 别把本文件读成"B 已经做完了")

| 没测的 | 为什么重要 |
|---|---|
| **子进程【崩了】怎么办** | 长驻 ⇒ 一次崩溃影响**之后所有**调用（现状是"崩了只影响这一次"）。恢复/重启策略**未设计也未实测** |
| **高并发 / 压力** | 只测到 **5 并发**。MCP 单会话是**请求-响应串行**的（探针里 5 个被串行化）⇒ **并发上限未探** |
| **生命周期归谁** | 那个 holder task 挂在哪（`main.py` 的 `startup`？谁取消它？`shutdown` 时怎么收？）—— **未设计** |
| **创空间上跑** | 那些数都是**本机**量的。创空间是 **2 vCPU / 8 GiB / Swap=0**，**未在那上面量过** |
| **② （常驻 HTTP/SSE）** | **本调研没做**。2.x 里形态齐备（服务端 `streamable_http_app`；客户端 `mcp/client/streamable_http.py` 与 `sse.py`）⇒ **可行 ≠ 已测**。⚠️ 没做的理由是 ① 已经决定性地赢（4–7ms，且不新增进程/端口），**⛔ 不是因为它不行** |

## 八 · 建议（供裁）

1. **① 值得做** —— 收益是**确定的、量过的**（`/agent/mcp_chat` 每次工具调用 2s → 5ms），
   代价是**84 MB 常驻 + 一套生命周期管理**。
2. 🔴 **但先把 §五 那个 stdout bug 修掉** —— 它与 B 独立、**现状就在发生**、且修法小（两行 + 一条守卫）。
   ⚠️ **而且它是 B 的前置**：长驻会话会让"启动时那一次 stdout 污染"的影响面从"每次调用一次"变成
   **"每个会话一次"** —— 数字上变好，但那说明**这根线本来就不该有噪声**。
3. ⛔ ** §2.2 的「执行统一」⛔ 不能单独做** —— 它会把另外**四条进程内直调**的链
   变成**每次 ~2 秒**。要做，**必须排在做完 ① 之后**。
