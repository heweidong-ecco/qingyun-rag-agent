## ✅ 做了什么

**真去抓 `cn.bing.com/search` 的结果页，解析出标题/链接/摘要。**

```python
BING_SEARCH_URL = "https://cn.bing.com/search"   # 2026-09-21 实测：本机网络下唯一直接可达的
BING_RESULT_SELECTOR = "li.b_algo"               # ⚠️ 逆向来的
SEARCH_TIMEOUT_SECONDS = 20                      # 网络往返上限
MAX_RESULTS = 8                                  # 只截【给 LLM 的条数】
```

解析 → `_parse_bing_results` → **解析不到就返回空列表**（不猜）→ `web_search` **如实报失败**。

## 🟡 做到哪 / 缺什么

| 缺口 | 说明 |
|---|---|
| 🔴 **靠逆向必应的 class 名** | `li.b_algo` / `.b_caption` 都不是稳定契约 ⇒ **必应改版即失效**。这是**已知并接受**的代价（替代品当时都不可达） |
| ⚠️ **依赖一个固定 UA 字符串** | 裸请求会被判机器人；写死 Chrome UA 是**绕过**，不是解决 |
| ⚠️ **没有重试 / 没有降级搜索引擎** | 一次失败就是"搜不到"。⚠️ **这是有意的**（见 §⚠️ 第 2 条） |
| ⚠️ **解析结果质量不受检** | 只判"有没有条目"，⛔ **不判条目是否相关** ⇒ 相关与否交给**下游的模型**判断 |

## ⚠️ 看代码会误判的地方

> ⭐ 这一节是整份 spec 的价值所在 —— 前面两节读代码也能推出来，这一节**推不出来**。

### 1. 🔴 2026-09-21 那次重写**根除的是一种具体的病** —— ⛔ 别把它加回来

**重写前**这里是**调 LLM 的 `enable_search` 扩展**，并把**模型返回的内容当成搜索结果**。
实测证据（写在模块 docstring 里，2026-09-21 实测）：

| 查询 | 当时返回的 |
|---|---|
| `2026年 诺贝尔物理学奖` | `<tool_call>{"name":"search",...}</tool_call>` ← **原始 tool_call 文本** |
| `今天北京天气` | 「北京今天（**2026年3月18日**）…14℃」 ← **编的**（当天是 2026-09-21，**差半年**） |
| `Python 是什么` | `<context>我需要了解用户所说的…` ← **模型的思考草稿** |

**根因**：`enable_search` 是**阿里百炼的私有扩展**，而本机 `.env` 走 DeepSeek ⇒ **被静默忽略**；
兜底只写在 `except` 里 —— **那次调用返回 200，兜底永远不触发**
⇒ 于是**未标记的模型输出**被当成搜索结果返回了。

⚠️ **三条里最危险的是天气那条**：格式漂亮、语气笃定、**日期全错** —— 调用方会直接采信。

🔴 **⇒ 谁想在这里加"搜不到就让模型先答一个"的兜底 —— 那正是这次重写要根除的病。**
`app/tests/test_search_tools.py` 有一条**结构判据**守着（本文件不许出现 LLM 客户端），不是靠自觉。

### 2. 🔴 "搜不到"是**返回值**，⛔ 不是异常 —— 判据是**前缀**

两条失败出口都返回**字符串**，都以「**搜索失败**」开头：

```python
return f"搜索失败：无法访问搜索引擎（{type(e).__name__}: {e}）。…"
return "搜索失败：结果页里【解析不到任何条目】—— 可能是必应页面结构变了，或被反爬拦截。…"
```

⇒ **函数从不抛异常**（`@tool` 的返回类型就是 `str`）。调用方要判成败**只能看前缀**。
⚠️ 这是**约定**，⛔ 不是类型 —— 而**约定不会被执行**（本仓立场：**「只有文字就漏，结构才执行」**）。

### 3. 🔴 `web_search` 的 **docstring 是写给 LLM 的**，⛔ 不是写给人的注释

```python
"""…⚠️ **如果返回以「搜索失败」开头**，说明这次**没搜到**…
   那种情况下请**如实告诉用户"暂时搜不到"**，
   ⛔ **不要拿你自己的知识假装成搜索结果** —— 那会让人以为这是查到的。"""
```

⇒ 这段会**进模型的上下文**，是**产品行为的一部分**。
⛔ **别把它当"啰嗦的注释"精简掉** —— 删掉它，模型就少一条"不许编"的指令。
（同族的还有 `interrupted_suffix` 那类「写给模型看的话」，改它们 = 改行为。）

### 4. ⚠️ `MAX_RESULTS = 8` 截的是**交给 LLM 的条数**，⛔ 不是抓取上限

抓的是**整个结果页**；只在前 8 条处切断（理由是"多了会冲上下文"）。
⇒ ⚠️ 所以「搜索结果有几条」在代码里**不是一个数**（页面上有多少条就是多少条）。

### 5. ⚠️ 每次调用都**真打一次外网**（20 秒超时）

⚠️ 与 `execute_python` 的 **5 秒**不是一回事：那是**沙箱执行**上限（子进程硬杀），
这是**网络往返**上限。**两个数字看着同类，量的是两件事。**
🔴 连带后果：`tool_health` 的启动自检里 `web_search: {"query": "test"}` ⇒ **每次启动/刷新健康检查都会打一次外网**
（见 `app/tools/specs/tool_health.md` §⚠️ 第 5 条）。

### 6. ⚠️ 用的是 `lxml` 解析器 —— ⛔ 别改成 `html.parser`

```python
soup = BeautifulSoup(html, "lxml")
```
两个解析器的**选择器行为不同**（尤其对畸形 HTML），换掉会**静默改变解析结果**
（不报错，只是条目变少/变多）。⚠️ 而 `lxml` 是**本仓已有依赖**（重写时刻意选的 0 新增依赖）。

### 7. ⚠️ 被摘掉的**浏览器类**工具与本文件**无关**

`fetch_webpage` / `screenshot_webpage` 已从 `mcp_server.TOOLS` 摘掉（依赖未安装的 chromium）。
⇒ ⛔ **别把"搜索需要浏览器"这个直觉套上来** —— 搜索结果页是**服务端渲染**的，
`httpx` 直接取就够；浏览器只在抓 **JS 渲染**的页面时才必要（那是 `browser_tools`）。
