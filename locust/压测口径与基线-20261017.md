## 〇 · 一屏结论（**先看这个，别先看表**）

| 问题 | 答案 |
|---|---|
| **横切面**（鉴权 + 限流中间件 + 路由）能扛多少？ | **3 把 key 下：9 并发 / 8.9 req/s，5 分钟 0 % 失败**（⚠️ **12 并发跑 5 分钟就 10.6 %** —— 30 秒那次是假象，见 §四·警告⑤） |
| 单把 key 呢？ | **≤3 并发**（≈3 req/s）—— **一把 key 一个桶**，这是硬上限 |
| 先到顶的是机器吗？ | ⛔ **不是** —— 10 并发时 `qingyun-rag-agent-api-1` 只用 **408 MiB / 3.84 GiB**、CPU **11 %** |
| 那是什么先到顶？ | 🔴 **用户级令牌桶 3 req/s**（按 `user_name`）⇒ **上限 ≈ 3 × key 数 req/s** |
| `/rag/search` 多快？ | **取决于改写缓存**：**缓存命中 ≈ 27 ms** · **未命中（冷路径）中位 3.4 s · p95 6.8 s · p99 7.9 s** |
| 慢在哪？ | **改写**（一次 **云端** LLM 调用 —— ⛔ **不是本地模型**）—— 单发取 `timing`：**改写 992–1383 ms**、检索只有 **148–342 ms**；压测里的冷路径**中位 3.4 s**（含排队与抖动）。那 1–3 秒**基本花在网络 + 云端推理上**，与这台机器的 CPU/内存无关 |
| `P99 < 800ms` 那个目标呢？ | **未达标** —— 冷路径 p99 **7.9 s**（差一个数量级）；**只有缓存命中时**才低于目标 |
| 能讲"高并发"吗？ | ⛔ **不能** —— 本机压不到全局限流（100/s），能到的只有"用户桶 × key 数" |

🔴 **一句话**：**先撞的是【按用户的限流】，不是 CPU/内存**；
而 `/rag/search` 的延迟**主要花在改写那次 LLM 上** —— **它的快慢几乎等于改写缓存的命中率**。

###  五条读数警告（不写这几条，表会被读歪）

1. **错误率 > 1 % 的延迟数一律【不可用】**（5 / 10 / 15 并发那几档）——
   失败大多是**快速失败的 429** ⇒ 混进平均会把延迟**拉低**，看着"更快"，**那是假的**。
2. **`QPS` 那列是【吞吐】，⛔ 不是【能力】**：它 ≈ 并发数；那些高 QPS 里**混着被拒的请求**。
3. **样本量决定 p99 可不可信**：30 s 的档只有几十到三百多个请求 ⇒ p99 就是"最慢的一两次"。
4. ⚠️ **别用"固定一句话"压检索**：改写结果**带 Redis 缓存**
   固定一句时中位数 **30 ms**、冷启动 **3.8 s** —— 那 30 ms **是缓存命中，不是检索**。
5. ⚠️ **30 秒的档会把"突发容量"当成"持续能力"**（本轮踩的第二遍）：
   令牌桶**突发 20** ⇒ 30 s 内看得见的只有"burst 吃掉了尖峰"。
   **实测**：u=12 跑 **30 s ⇒ 0 %**；跑 **5 min ⇒ 10.59 %**。
   ⇒ **并发档位一律以 ≥5 分钟的数为准**；30 s 的数只能当"冒烟"。
6. ⚠️ **18 句的问题池也会把缓存算进去**：2 组各 200 次 ⇒ 每句重复约 11 次 ⇒ 约 89 % 命中。
   ⚠️ **那个"命中率"是压测自己造出来的**，⛔ 不是产品的缓存命中率。
   ⇒ 要量冷路径，必须 `BENCH_UNIQUE=1`（每次换一句 ⇒ 必然 miss）。

## 五 · 为什么先撞的是「用户级限流」（根因 · 判据 · 出路）

本仓有**两层**令牌桶（`app/main.py::RateLimitMiddleware`）：

| 层 | 参数（`app/billing/token_config.py`） | 桶键 |
|---|---|---|
| **全局** | `rate=100/s` · `capacity=150` | `global` |
| **用户** | `rate=3/s` · `capacity=20` | `rate_limit:{user_name}` |

⇒ **一把 key = 一个 `user_name` = 一个桶**。稳态需求 ≈ 并发数 req/s：

| key 数 | 供给 | **持续**干净上沿（≥5 分钟） |
|---:|---:|---|
| 1 | 3 req/s | **3 并发**（⚠️ 单 key 的 5 分钟档**没跑**；30 s 那组与算术一致：3 并发 0 %、5 并发 10.2 %、10 并发 48.0 %） |
| 3 | 9 req/s | **9 并发 / 8.91 req/s**（5 min · 2668 请求 · **0 %**）· **12 并发跑 5 分钟 10.59 %** |

📌 **判据（可打印）**：

```bash
grep -n "GLOBAL_LIMIT_RATE\|GLOBAL_LIMIT_CAPACITY\|USER_LIMIT_RATE\|USER_LIMIT_CAPACITY" app/billing/token_config.py
grep -n "rate_limit:" app/access/rate_limiter.py
```

###  它 不是缺陷 —— 是产品有意做的成本闸

本仓把「**成本闸在工作**」与「**服务坏了**」当**两件事**。
⇒ 429 是**设计内的回答**；那几档真正测到的是**这条限流本身**，⛔ 不是"服务在 15 并发下的延迟"。

### 出路（三条，按代价排）

| # | 办法 | 代价 | 状态 |
|---|---|---|---|
| ① | **只报干净带**（单 key ≤3 · 3 key ≤12） | 拿不到"更高并发" | ✅ **本文现状** |
| ② | **加 key**（每把 +3 req/s） | 要建 key + 把池子传给压测件 | ✅ **已做**（`RAG_API_KEYS` 支持任意把） |
| ③ | 压测时**临时调高**限流 | 测的就不是产品了 | ⛔ **不做** |

⚠️ **全局限流（100/s）在本机够不到** —— 3 把 key 只到 ~12 req/s，离 100 还差一个数量级
⇒ 这一层**本轮一次都没触发**（见 §五·附）。

## 五·附 · **其他硬限制：哪一层触发了、怎么认出来**（作者 要求）

本仓不止"限流桶"一种硬限制。**它们都回 429、`code` 还基本一样** ⇒ 必须按**各自的痕迹**分辨：

| 层 | 参数 / 键 | 本轮实测 | 触发时的**痕迹** |
|---|---|---|---|
| **用户**令牌桶 | `3/s` · 突发 `20` · 键 `rate_limit:{user}` | ✅ **触发了**（5 / 10 / 15 并发档） | 响应头 `X-RateLimit-Limit=20` · `X-RateLimit-Remaining=0`；**无** `retry_after` |
| **全局**令牌桶 | `100/s` · 突发 `150` · 键 `global` | ❌ **一次都没触发**（本机压不到 100 req/s） | 响应体 `retry_after` + 头 `Retry-After: 60` |
| **会话级额度**（B8） | 按 `(user, thread)` | ❌ 未触发（付费档**每人一个 `thread_id`**，故意避开） | `code=QUOTA_EXCEEDED` + **`scope=session`** |
| **全站日熔断**（B11） | `15 000 000` LLM token/天 | ❌ 未触发（当天全站已用 ≈ **3.5 k**） | `scope=global` |
| **用户日额度** | free：LLM `50 000` / embedding `10 000` | ❌ 未触发（付费档每人约 8 次 × ~300 token） | `code=QUOTA_EXCEEDED` + `X-Quota-Pool` |
| **单次 / 单线程成本预算** | Agent 链专用 | ❌ **未覆盖**（没压 Agent 真链，见 §七） | —— |

**三条结论**：
1. **真正先到顶的是"用户令牌桶"**，其余几层在这台机器上**够不到**；
2. **只看 `code` 分不出"全局"与"用户"两层** —— 它们共用 `RATE_LIMITED`，
   必须看 `Retry-After` / `retry_after` 与 `X-RateLimit-*` 那两组痕迹；
3. ✅ **压测件已按这张表实现**：失败信息里带 `layer=user` / `layer=global` + `code` + `scope` + 限额
   （补）⇒ locust 的错误报表**按限制种类分行**，⛔ 不再是一句没信息的 `429 Client Error`。

## 六 · 对照（** 做了一组**：改写 开/关）

> 需求单原话：「**"回路"的证据 = 至少一组对照**（改了某处 → 数字变了）。
> 没有对照，就只写「跑过一次基线」，⛔ 不写"多轮优化"。」

| 变量 | 一边 | 另一边 | 数字变化 |
|---|---|---|---|
| **查询改写**（`fast` vs `accurate_norerank`） | **`fast`**：不改写 · 5 min · **211** 样本 | **`accurate_norerank`（强制 miss）**：改写 · 3 min · 63 样本 | **p50 27 ms → 3400 ms**（**约 126 倍**）· p95 350 ms → 6800 ms · p99 **450 ms → 7900 ms** |

**这一组回答的是**：「改写那一次 LLM 值不值 3 秒？」——
数据说：**冷路径下它把中位延迟从 28 ms 拉到 3.4 s**；而**缓存命中时几乎不额外花时间**（27 ms）。
⇒ 所以真正的杠杆**不是"改不改写"，是"改写缓存命中率"**。

⚠️ **口径说明（⛔ 别读成"改了代码就变快"）**：这组是**同一套代码、换 `mode` 参数**（`BENCH_MODE`），
所以它是「**两个功能档**的对照」，⛔ **不是"优化前后"**。
⇒ 能据此说「**我们做过对照**」，⛔ **不能据此说"多轮优化把 X 从 A 降到 B"**（那是另一件事）。

**可做但没做的两组**（下次直接抄）：重排序 开/关（要装 torch）· workers 数。

| 没压 | 为什么不压 |
|---|---|
| **流式**（`/rag/stream_search` · `/agent/*/stream`） | ① **每次请求真调 LLM** ⇒ 花钱；② 流式的延迟主要由**上游模型吐字速度**决定 ⇒ 压出来的是**模型**的表现，⛔ 不是我们的服务；③ 一条流式连接要**活几秒到几十秒**，并发数直接换算成长连接数 ⇒ 本机 3.84 GB 撑不起有意义的高并发，**结论会是"机器不行"而不是"代码不行"** |
| **登录**（`/auth/login`） | ① 它做的是 **pbkdf2 口令哈希（故意慢）** —— 压出来的数字是"**哈希成本**"，与产品性能无关，而调快它就是**降低安全性**；② 每次登录**写审计/令牌** ⇒ 会污染库；③ 它**不在任何业务链路上**（一次登录换 15 分钟令牌，之后不重复） |
| **Agent 真链**（`/agent/*_chat` · 非流式与流式） | ① **每次调用真调 LLM + 工具，且每次工具调用新起一个 MCP 子进程** ⇒ 花钱 + 进程数爆炸；② **不可复现**（模型侧延迟抖动远大于我们服务本身）；③ 8 GB / 3.84 GB 起不了有意义的并发（`docker-compose.yml` 里 executor 只分到 256 MiB） |

**一句话**：**这三类测出来的主语都不是"我们的服务"** ——
本仓要的是「**我们这一段**在固定环境下的表现」，所以只压**鉴权 / 限流 / 路由 / 检索**这几段。

## 八 · 怎么跑（可复现）

```bash
# 0) 先核实本机状态（裁定原话）
docker ps --format '{{.Names}}' | grep eval        # ⇒ 必须为空
docker stats --no-stream                            # ⇒ 记下当时的资源占用

# 1) 起环境
docker compose up -d api                            # 顺带起 postgres / redis / executor
docker ps --format '{{.Names}}\t{{.Status}}'        # ⇒ qingyun-rag-agent-api-1 healthy

# 2) 建 key（🔴 用 --out：它把 key 写进 600 权限的文件，stdout 只打路径）
./venv/bin/bench1 --days 7 --out <仓外凭据目录>/bench-key-1.key
#    ... bench2 / bench3 同理（一把 = 一个桶 = +3 req/s）

# 3) 把池子交给压测件（⛔ key 别进管道 / 日志 / 会话记录）
export RAG_API_KEYS="$(cat 路径1),$(cat 路径2),$(cat 路径3)"
export RAG_BASE_URL=http://localhost:8000

# 4) 免费档（零花费）
./venv/bin/locust -f locust/locustfile_bench.py --headless -u 12 -r 3 -t 60s --only-summary

# 5) 付费档（🔴 每次请求真调 embedding + 改写 LLM ⇒ 花钱；并发压小）
BENCH_PAID=1 ./venv/bin/locust -f locust/locustfile_bench.py --headless -u 9 -r 3 -t 300s --only-summary

# 5b) 两个开关（本轮的对照与冷路径就靠它们）
#   BENCH_MODE=fast|accurate_norerank|accurate|full   打哪个档（默认 accurate_norerank）
#   BENCH_UNIQUE=1                                     每次换一句 ⇒ 强制改写缓存 miss（量冷路径）
BENCH_PAID=1 BENCH_MODE=fast ./venv/bin/locust -f locust/locustfile_bench.py --headless -u 9 -r 3 -t 300s
BENCH_PAID=1 BENCH_UNIQUE=1  ./venv/bin/locust -f locust/locustfile_bench.py --headless -u 9 -r 3 -t 180s
```

⚠️ **用 `./venv/bin/locust`**（本仓的 locust 在 venv），⛔ 别用系统 `python3` / `locust`。
⚠️ **档间冷却 ≥ 15 s**（桶回满）。
⚠️ **并发档位以 ≥5 分钟的数为准**（§四·警告⑤：30 秒会被突发容量骗过去）。
