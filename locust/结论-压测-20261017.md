# 压测 · 结论报告

> 🔴 **一句话**：**系统先撞的是"按用户的限流"，不是机器**；
> 而 `/rag/search` 慢的原因**不在检索**，在**改写那一次【云 API】调用** —— 所以**加本机硬件基本没用**。

## 一 · 五个结论

### 1. 横切面（鉴权 + 限流中间件 + 路由）扛得住 **9 并发 / 8.9 req/s**

- **3 把 key · 9 并发 · 5 分钟**：**2662 个请求 · 0 % 失败** · p99 **88 ms**。
- ⚠️ **12 并发跑 5 分钟就 10.60 %**（全 429）。
- ⚠️ **别拿 30 秒的档当能力**：u=12 跑 **30 秒是 0 %** —— 那是**令牌桶的突发容量（20）**吃掉的，
  不是真的扛得住。

### 2. 上限 = **3 req/s × key 数**，而且**先到顶的不是机器**

- 一把 key = 一个 `user_name` = 一个令牌桶（`3/s`，突发 `20`）。
- **跑 10 并发时** `qingyun-rag-agent-api-1` 只用 **408 MiB / 3.84 GiB**、CPU **11 %** ⇒ **资源远没到顶**。
- ⇒ 想压更高，**加 key**（每把 +3 req/s），⛔ 不是加内存。

### 3. `/rag/search` 的快慢 = **改写缓存的命中率**

| 配置 | 样本 | p50 | p95 | p99 |
|---|---:|---:|---:|---:|
| `fast`（**不改写**） | 211 | **27 ms** | 350 ms | **450 ms** |
| `accurate_norerank`（**缓存命中**） | 205 | **27 ms** | 98 ms | 3300 ms |
| `accurate_norerank`（**强制 miss = 冷路径**） | 63 | **3400 ms** | 6800 ms | **7900 ms** |

⇒ **同一个端点，冷热差 ~126 倍。** 命中时和"完全不改写"一样快；未命中时中位就 3.4 秒。

### 4. 🔴 那 3.4 秒**不是本机算出来的** —— **改写走的是【云 API】**

- `app/rag/query_rewriter.py` → `core.llm_factory.make_llm()` → **`.env` 的 `LLM_BASE_URL`**
  （现为 **`https://api.deepseek.com`**）· 模型 **`deepseek-v4-flash`**。
- 🔴 **本仓没有跑任何本地模型 / 本地 LoRA / 本地推理。**
- ⇒ **这 3.4 秒主要是【网络 + 云端推理】**，⛔ **与这台 4 vCPU / 8 GB 的机器无关**；
  换更快的机器**基本不会改善**它。
- 📌 单发取 `timing` 也能佐证：**改写 992–1383 ms**，而**检索本身只有 148–342 ms**。

### 5. 目标与实测差一个数量级（要如实写）

| README 的目标 | 实测 |
|---|---|
| `P99 检索延迟 < 800ms` | **冷路径 p99 7900 ms**（差约 10 倍）；**只有缓存命中时**才低于目标 |
| `基础检索失败率 < 0.1%` | ⚠️ 冷路径 **0 / 63** —— 「没观察到失败」，**样本不算多** |
| `Embedding 缓存命中率 > 90%` | ⬜ **仍未实测**（但已测到**改写**缓存的影响：冷热差 ~126 倍） |

| 变量 | 一边 | 另一边 | 变化 |
|---|---|---|---|
| **查询改写 开/关** | `fast`：p50 **27 ms** | `accurate_norerank` 冷路径：p50 **3400 ms** | **约 126 倍** |

⇒ 能说「**做过对照**」，⛔ 不能说「**多轮优化把 X 从 A 降到 B**」。

## 三 · 没测什么、为什么（别读成"都测了"）

| 没测 | 为什么不测 |
|---|---|
| **流式**（`/rag/stream_search` · `/agent/*/stream`） | 每次真调 LLM（花钱）· 延迟由**上游吐字速度**决定（测的是模型）· 长连接 ⇒ 并发数=连接数，3.84 GB 撑不起 |
| **登录**（`/auth/login`） | 做的是 **pbkdf2（故意慢）** ⇒ 测出来是"哈希成本"，调快 = 降安全性；且**不在业务链路上** |
| **Agent 真链** | 每次真调 LLM + 工具，**每个工具调用新起一个 MCP 子进程** · **不可复现**（模型抖动） |
| **重排序那两档**（`accurate` / `full`） | **要 torch**，本镜像没装 |
| **Embedding 缓存命中率** | 还没设计出口径 |

**共同点**：这些测出来的**主语都不是"我们的服务"**。
⇒ 本轮压的是**我们这一段**：鉴权 / 限流 / 路由 / 检索编排。

## 四 · 下一步（按性价比排，都还没做）

| # | 做什么 | 为什么它排这个位置 |
|---|---|---|
| 1 | **提高改写缓存命中率**（或给它一个更聪明的键口径） | 它是**唯一的大杠杆**：命中 27 ms / 未命中 3400 ms |
| 2 | **默认档要不要留在 `accurate_norerank`** | `fast` 只要 27 ms；这是**产品取舍**，不是性能问题 |
| 3 | 换更快的改写模型 / 更强的超时与降级 | 3.4 s 在云 API 上 ⇒ 动模型比对机器有用 |
| 4 | 🔵 **改写换成【本地自训练 LoRA 模型】**（见下方专条） | 它**换掉的不是快慢，是"延迟归谁"** —— 从云 API 变成本机推理 |
| 5 | 加 key 才能压更高（每把 +3 req/s） | 本机 CPU 还没到顶，瓶颈是限流 |
| 6 | 补 Embedding 缓存命中率 | README 里唯一还是 ⬜ 的那格 |

### 关于第 4 条（**本地自训练 LoRA 改写模型**）—— 它改变的是"哪个资源在承重"

现在改写是**一次跨公网的云 API 调用** ⇒ 那 1–3 秒主要是**网络 + 云端推理**，
本机再强也影响不到它。若改成**部署在本机的、自己训的 LoRA 小模型**：

| 面 | 会怎么变 |
|---|---|
| ✅ **拿掉的** | **网络往返**与**按 token 计的调用成本**；改写文本不出本机 |
| ✅ **拿到的** | 延迟变成**本机推理时间** ⇒ **从此"加硬件"才成为一个有效变量**（现在它不是） |
| ⚠️ **要付的代价** | ① **本机要留出推理资源** —— 这台是 4 vCPU / 8 GB，**Docker 只分到 3.84 GB**，模型多大、能不能常驻，得先量；② **首次加载**与**冷启动**要单独算；③ **质量要单独评** —— 改写训得好不好，直接决定检索质量，⛔ 不能拿"快"换掉"对"；④ 有 GPU / 更大内存时它才是明显划算的选择 |
| 📌 **一句判据** | 换之前先量一件事：**本机推理的 p50 能不能低于现在云 API 的 3.4 s**。⛔ 别只按"本地一定更快"推断 —— **小模型在 4 vCPU 上未必跑得赢一次云端 API** |

⚠️ ** 不要做的事**：**为了"改善检索延迟"去加本机内存/CPU** —— 在那 3.4 秒还是**云 API** 的时候，它**不起作用**。
（⚠️ 一旦真做了第 4 条、改写落到本机，**这条就反过来成立** —— 那时硬件才是变量。）
